# Per-key routing profiles with an explicit selection pipeline

## Overview
- Every inbound client API key (an entry of `access.api-keys`) gets its own routing profile of four stages: (1) sticky session, (2) preferred subscription per provider (claude, codex), (3) explicit pool strategy = primary + tiebreak, (4) Claude -> Codex fallback. A key without a profile uses the shared profile, which is the existing global routing configuration. A key with a profile uses it completely; there is no per-field inheritance.
- Problem: today several mechanisms shape a new credential selection in a hidden order (quota reserve levels, then the global preferred account, then the highest Priority tier, then the configured strategy), and they apply the same way to every client key. The user wants a key to keep consuming its assigned subscription while that subscription is usable, without hopping between accounts, and wants the order of selection to be explicit.
- Benefits: per-key assignment of subscriptions so parallel projects do not compete for one account; an explicit `selection {primary, tiebreak}` with no hidden Priority or reserve layer; the fallback to Codex uses the same key's Codex preference and strategy.
- Integration: the profile is resolved once per execution in the auth manager (`sdk/cliproxy/auth`) and carried in the context, the way the global preferred accounts are carried today. The existing selectors become pickers inside one pipeline selector. The management API gains `GET /v8/management/routing/profiles`; writes go through the existing v8 config PATCH. The panel UI is a separate plan in CPA-Manager-Plus.

## Decisions
- **Context**: the current new-selection order is `availability -> quota reserve filter -> global preferred account -> highest Priority tier -> strategy` (`sdk/cliproxy/auth/selector.go:503-532`), with session affinity wrapping it (`selector.go:1018`) and the opt-in Claude -> Codex fallback after a failed Claude round (`sdk/cliproxy/auth/claude_fallback.go`, commit f7a5cd17). The global preferred account is a single map for all clients (`preferred_accounts.go`). The inbound key principal is already available to the manager through the gin context (`internal/api/server_middleware.go:169,227` sets `userApiKey`; `sdk/api/handlers/handlers.go:543` stores the gin context under the `"gin"` key; `session_resolver.go:24` and `conductor_home.go:463-475` read it).
- **Chosen approach** (approved in brainstorming on 2026-11-04, refined by the grill round the same day):
  1. **Config.** `routing.selection {primary, tiebreak}` and `routing.key-profiles` (a map keyed by the raw client API key string) are added to `RoutingConfig`. A profile is `{session-affinity, preferred-accounts, selection, claude-fallback}` with the same shapes as the global fields. Slot values: narrowing criteria `priority`, `reserves`, `earliest-reset`, `most-remaining`; pickers `round-robin`, `weighted-round-robin`, `fill-first`. When `routing.selection` is absent, the effective selection is derived as `{primary: reserves, tiebreak: <legacy routing.strategy, default round-robin>}`. Normalize is lenient everywhere it runs (startup, hot reload, Home, the management parse path): it validates slots and fallback blocks, drops `null` profile entries, and drops profiles whose key is not in `access.api-keys` with a warn log that prints only a sha256 prefix. Strict rejection of unknown keys happens in the v8 config handler only.
  2. **Profile resolution.** The public `Execute`, `ExecuteCount`, and `ExecuteStream` resolve the effective profile once (key profile, else shared) into a `routingProfile` value and inject it into the context before the fallback wrapper decides anything; the private `execute*` functions inject only when the context carries none. The profile is the single context carrier for preferences and the fallback block; `preferredAccountsContextKey` is removed. Home mode resolves no profile. A plugin scheduler resolves the shared profile only, so global preferences keep applying there as today while key profiles and the fallback stay native-only.
  3. **Preference before soft reserve.** For a new selection the profile's preferred account of the provider is taken first when it is available and not held by a hard reserve, even at soft1-3. Disabled, cooldown, model support, and hard reserve still block it. Soft levels rank only the remaining pool. The preference lives in the pipeline only; the legacy availability helpers keep their behavior for standalone SDK use of the old selectors.
  4. **Pipeline.** One `PipelineSelector` applies primary then tiebreak over a pipeline-specific candidate set: every priority tier, blocked and hard-reserved credentials removed, no soft filter, no tier narrowing. Narrowing criteria keep the best group (reserves = `quotaReserveFilter`'s selectable result; priority = `highestPriorityAuths`; earliest-reset = the loop extracted from `EarliestResetSelector.Pick`, unknown resets excluded when any is known; most-remaining = the highest minimum remaining percent from a `subscriptionWindows` helper extracted from `quotaReserveLevel`, unknown excluded when any is known). Pickers choose one credential by delegating to `RoundRobinSelector`, `WeightedRoundRobinSelector`, `FillFirstSelector` in a picker-only context that disables their own reserve, tier, and preference narrowing. Leftover ties go to round-robin; for legacy `strategy: earliest-reset` this moves equal-reset ties from stable lowest ID to round-robin. A picker as primary makes the tiebreak inactive. The slots come from the context profile at `Pick` time, and the shared slots are read from the runtime config at `Pick` time, so one selector serves every key and a selection change never rebuilds the selector.
  5. **Sticky per key.** The `SessionAffinitySelector` wrapper is built when sticky is enabled in the shared profile or in any key profile. `Pick` consults the context profile and, when sticky is off for that key, skips the LCP matcher, the cache lookups, and every `bind()`, and marks the request so `OnResult` neither refreshes nor deletes bindings. When the inner selector is the pipeline, the cold path hands it the across-tier hard-only candidate set instead of `newSelectionAuths`. TTL and subagent affinity stay global. Toggling the wrapper on or off rebuilds the selector and resets bindings; a selection or preference change does not.
  6. **Scheduler fast path.** `PipelineSelector` is deliberately not a built-in selector, so `useSchedulerFastPath` stays false and `pickNext`/`pickNextMixed` always take the legacy path while the pipeline is active. The scheduler would otherwise reapply the hidden Priority tier.
  7. **Fallback.** `executeWithClaudeFallback` reads the profile's fallback block; the Codex leg (`claude_fallback.go:94`) runs with the same context, so stages 1-3 use the key's Codex preference and selection. The direction stays Claude -> Codex only.
  8. **Management API.** New `GET /v8/management/routing/profiles` returns `{supported, shared, keys, selection_options}`; accounts and models come from the existing `GET /v8/management/credentials` and `GET /v8/management/routing/claude-fallback`. Writes use the existing `PATCH /v8/management/config`; a `null` profile entry deletes the profile. The handler rejects a profile for a key missing from `access.api-keys` with 400 before parsing; invalid slot values fail inside `ParseConfigBytes` and return 422 like every other parse error. The comment-preserving saver prunes `routing.key-profiles` to the generated keys so a deleted, rotated, or nulled key never stays on disk. `PATCH /v8/management/api-keys {old,new}` moves the profile to the new key; `PUT`, index patches, and deletes drop profiles of keys no longer listed.
  9. **Observability.** One structured logrus line per profile-driven selection with the key hash prefix, the deciding stage, provider, and auth index. Never the raw key.

## Technical Details
- **Config** (`routing:`):

  ```yaml
  routing:
    session-affinity: true
    session-affinity-ttl: 24h
    preferred-accounts: {claude: "auth-index-a", codex: "auth-index-b"}
    selection: {primary: reserves, tiebreak: earliest-reset}
    claude-fallback: {enabled: true, mode: auto, mappings: [{from: "claude-opus-*", to: "gpt-6-astra"}]}
    key-profiles:
      "<client api key>":
        session-affinity: false
        preferred-accounts: {claude: "auth-index-c"}
        selection: {primary: priority, tiebreak: round-robin}
        claude-fallback: {enabled: true, mode: auto, mappings: [{from: "claude-*", to: "gpt-6-sol"}]}
  ```

  `strategy` stays accepted; it only feeds the derived selection when `selection` is absent.
- **Effective selection**: `Selection.Primary != ""` ? `Selection` : `{reserves, legacy(Strategy) or round-robin}`.
- **Profile lifetime**: resolved in the public `Execute*` from the gin `userApiKey`; carried by one context value through the fallback wrapper, retries, and the Codex leg. Home: none. Plugin scheduler: shared only.
- **Pipeline** (new selection, per provider):

  ```
  available = every tier, not disabled, not cooling down, supports model, not under an active hard reserve
  if profile.preferred[provider] in available: return it            # stage 2
  group = available
  for slot in [primary, tiebreak]:
      if slot is narrowing: group = narrow(slot, group)             # best group only
      if slot is picker:    return picker(slot).Pick(group)          # picker-only context, stop here
  return roundRobin.Pick(group)
  ```

  Narrowing semantics: `reserves` keeps `quotaReserveFilter`'s selectable set (lowest active soft level); `priority` keeps the highest priority; `earliest-reset` keeps the earliest known future reset and drops unknowns only when a known one exists; `most-remaining` keeps the highest minimum remaining percent and drops unknowns only when a known one exists.
- **Sticky**: bound-session validation stays as today (across priorities, no reserve); the decision to look up and to write a binding depends on the profile flag; `session-affinity-disabled` in the request metadata makes `OnResult` a no-op. Rebuilding the wrapper resets bindings; selection edits do not.
- **Scheduler**: the pipeline is not a built-in selector, so the fast path is off and `pickNext`/`pickNextMixed` use the legacy selector path.
- **Fallback**: unchanged `shouldFallbackClaude` rules; the Codex leg carries the same context profile.
- **API**:
  - `GET /v8/management/routing/profiles` -> `{supported, shared, keys, selection_options}`
  - `PATCH /v8/management/config` with `{"routing": {"selection": {...}}}` or `{"routing": {"key-profiles": {"<key>": {...} | null}}}`; unknown key -> 400 `unknown_api_key`; invalid slot -> 422 `invalid_config`
  - `PATCH /v8/management/api-keys {"old","new"}` moves the profile; `PUT`, index patches, and `DELETE` drop profiles of keys no longer listed
  - the saver prunes `routing.key-profiles` to the keys present in the generated config
- **Log line**: `Routing profile selection` with `routing_key=<12 hex>`, `routing_stage`, `provider`, `auth_index`; inside the Codex fallback leg `routing_stage=fallback` plus `fallback_stage=<deciding stage>`.
